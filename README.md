# Синхронизация CRM → PostgreSQL

Решение тестового задания: ускорение ночной синхронизации
20 тыс. покупателей и 50 тыс. сделок. Точка входа —
`collect_leads_customers(is_full=True)`. Python ≥ 3.9, Flask, SQLAlchemy 2.0, PostgreSQL.

## Что было дорого

На каждую сущность выполнялись поиск внутри JSONB, запись и commit.
Без индексов поиск мог сканировать всю таблицу; после commit ORM мог повторно
загружать объекты. В конце таблица читалась ещё раз для очистки, а JSON-массивы
переписывались многократно. Число обращений к БД составляло сотни тысяч.

## Что изменено

1. Таблица читается одним SELECT через серверный курсор, без ORM identity map.
2. Сопоставление по CRM ID и логину выполняется по словарям в памяти.
   Неоднозначность логина считается по различным записям-владельцам;
   при обновлении логина и слиянии индексы поддерживаются в актуальном состоянии.
3. После успешного завершения обеих выгрузок полный прогон очищает отсутствующие
   сущности и сущности с «удалить» в имени. Пустые записи удаляются.
4. Изменения сохраняются multi-VALUES INSERT / UPSERT, удаления — пакетами IN,
   до 1000 строк. Неизменённые записи не записываются. Весь прогон выполняется
   в одной транзакции: один commit при успехе, rollback при любом исключении.

Исправлены ошибки бизнес-логики: покупатели без логина пропускаются, поиск по CRM ID
имеет приоритет, неоднозначный логин не используется. При слиянии сохраняется
владелец сделки и применяется её текущая версия; переносятся вложения, метки
присутствия и настройки уведомлений. Сделка без совпадений создаёт новую запись,
в том числе без логина. Контакты и компании из `_embedded` сохраняются;
отсутствующее имя не ломает очистку. Ошибки выгрузки больше не скрываются.

## Что оставлено и почему

- **JSONB и общий `AbstractCustomer`** сохранены для совместимости с исходными
  данными. Сделки и покупатели связаны принадлежностью к одной записи.
  Два GIN-индекса `jsonb_path_ops` поддерживают `@>` по CRM ID, точному логину
  и полному названию. Поиск по подстроке потребует отдельного индекса.
- **Снимок в памяти** сокращает обращения к БД при заданном объёме. Цена — память
  под все сохранённые JSON и индексы, перезапись изменённого JSONB целиком
  и дополнительные затраты при длинных цепочках слияний.
- **Блокировка `SHARE ROW EXCLUSIVE`** защищает снимок от другого прогона
  и параллельных изменений. Обычные SELECT работают, писатели ждут до конца
  синхронизации, включая получение CRM. Ожидание получения блокировки самим
  прогоном ограничено 5 секундами. Это компромисс для ночного задания.
- **Частичный режим** сохраняет исходные исключения статусов: 111349 у покупателей
  и 143 у сделок. Очистки в нём нет; полный режим эти статусы не пропускает.
  Успешная пустая полная выгрузка очищает таблицу. Дубли сохранённых CRM ID
  в покупателях/сделках останавливают прогон до записи как повреждение данных.
- **Боевой CRM-клиент, Celery и брокер** не реализованы по условию.
  `amocrm_get` явно поднимает `NotImplementedError`; для проверки используются DTO
  и подставной итератор. Дополнительных сервисов, кроме PostgreSQL, нет.

## Оценка запросов и памяти

Для пакета B число основных SQL-команд равно
`3 + ceil(U/B) + ceil(I/B) + ceil(D/B)`, где U, I, D — количества изменённых,
новых и удаляемых **агрегатов**, а 3 — SET, LOCK и SELECT. BEGIN/COMMIT отдельно.

| Сценарий, B = 1000 | Основные SQL-команды | Commit |
| --- | ---: | ---: |
| 70 тыс. новых либо изменённых агрегатов, без удалений | 73 | 1 |
| 20 тыс. новых либо изменённых агрегатов, без удалений | 23 | 1 |
| Удалить 70 тыс. старых и вставить 70 тыс. новых | 143 | 1 |

Смесь вставок и обновлений может добавить один неполный пакет. Серверный курсор
дополнительно делает примерно `ceil(S/B)` FETCH для S старых строк, плюс операции
открытия/закрытия и граничные FETCH. Для 70 тыс. старых изменяемых агрегатов
получается около **150 обращений к PostgreSQL**. Повторного SELECT таблицы нет.

Память — `O(сохранённые JSON + индексы + вложенные связи + SQL-пакет)`.
Вся CRM-выгрузка отдельным списком не накапливается. Небольшой синтетический замер
на Python 3.12 / macOS: 2 тыс. покупателей + 5 тыс. сделок, отдельные владельцы,
один контакт и дополнительная строка 1 КиБ на сущность дали ≈41 МиБ Python peak
и ≈108 МиБ RSS без трассировщика. Экстраполяция на 20/50 тыс. — ≈412 МиБ
Python-объектов и ≈580 МиБ RSS; с запасом на драйвер и сериализацию пакета —
**0,6–0,9 ГиБ на процесс для такого наполнения**. Это оценка, а не полный прогон:
реальный размер `api_value`, число вложений и накопленная история неизвестны.

## Запуск проверок

Нужны uv и Docker Compose либо доступный PostgreSQL. Команды из корня репозитория:

```bash
uv sync --locked --python 3.12
docker compose -p crm_sync_test up -d --wait
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
docker compose -p crm_sync_test down
```

Проверено: **36 тестов прошли на Python 3.12 и PostgreSQL 16**. Покрыты сопоставление,
слияния, очистка, обрыв обоих итераторов, откат посреди записи, блокировка писателя,
применимость GIN и число SQL-пакетов. Для 135 строк и пакета 32 проверяются
8 основных SQL-команд и один commit.

Для своего PostgreSQL задать `TEST_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:PORT/some_test`.
Тесты создают и удаляют отдельную случайную схему; имя БД должно оканчиваться
на `_test`, пользователь должен иметь право создавать схемы. По умолчанию Compose
использует локальный порт 55439; при изменении `POSTGRES_PORT` изменить и URL тестов.

Воспроизвести оценку памяти без CRM и БД (macOS/Linux):

```bash
uv run python -m scripts.estimate_memory
uv run python -m scripts.estimate_memory --trace-python
```

## Подключение к приложению

В существующем Flask-приложении инициализировать `db` из `models.py` через
`db.init_app(app)`, указав `SQLALCHEMY_DATABASE_URI` вида `postgresql+psycopg://...`.
В контексте `app.app_context()` вызвать:

```python
from main import collect_leads_customers

stats = collect_leads_customers(is_full=True, fetch=crm_fetch, batch_size=1000)
```

`crm_fetch` — внешний клиент с сигнатурой `(entity_class, _with=...)`, выдающий
`Customer` или `Lead` из `amocrm.py`. Поле `custom_fields_values` — словарь
`имя → {"value": значение}`, `_embedded` содержит списки контактов/компаний с `id`.
Ошибка любой страницы должна выходить наружу: тихое усечение выгрузки невозможно
отличить от успешного завершения. Функция владеет отдельной транзакцией;
вызывать без несохранённых ORM-изменений.

На новой БД создать таблицу и индексы через `db.create_all()` в контексте приложения.
Для существующей таблицы применить миграцию **вне транзакции**:

```bash
psql "postgresql://USER:PASSWORD@HOST:5432/DB" -v ON_ERROR_STOP=1 -f migrations/001_search_indexes.sql
```

Пользовательский поиск по условию не реализован; пример поддерживаемого запроса:

```sql
SELECT id FROM abstract_customer
WHERE amo_leads @> '[{"general":{"name":"Название сделки"}}]'::jsonb;
```
